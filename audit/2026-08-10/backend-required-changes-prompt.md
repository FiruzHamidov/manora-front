# Единый промпт для обязательных backend-изменений Manora

Работай только в репозитории `/Users/sarvat/Documents/GitHub/manora-backend`. В рабочем дереве уже могут быть незавершённые изменения другого разработчика: не удаляй, не откатывай и не перезаписывай их. Перед изменениями изучи текущие `AuthController`, `UserController`, `SmsAuthService`, `PhoneNormalizer`, policies/gates, модель `User`, миграции и `routes/api.php`.

Нужно реализовать два независимых контракта, которые уже ожидает frontend.

## 1. Регистрация и автоматический вход по телефону и SMS

Добавь публичный throttled endpoint:

```text
POST /api/sms/register
```

Запрос:

```json
{
  "phone": "+992918555581",
  "code": "123456"
}
```

Требования:

1. Валидируй телефон и шестизначный код. Нормализуй номер существующим `PhoneNormalizer`/`SmsAuthService` точно так же, как `/sms/request` и `/sms/verify`.
2. Проверяй одноразовый код с purpose `registration`, TTL и лимитом попыток. После успешной транзакции код должен быть потреблён; повторное использование запрещено.
3. В одной DB-транзакции повторно проверь отсутствие пользователя по нормализованному телефону и создай активного пользователя:
   - роль `user`, fallback `client`;
   - `auth_method=sms`;
   - системное имя вида `Пользователь 5581`;
   - клиент не передаёт пароль. Если колонка обязательная — `Hash::make(Str::random(64))`;
   - onboarding/auth state должны разрешать базовый вход и последующее заполнение профиля.
4. Исключи race condition: параллельные запросы для одного телефона не создают дубль. Используй unique constraint/lock и корректно преобразуй конфликт в `409`.
5. Ответ `201` должен совпадать с контрактом успешного входа:

```json
{
  "token": "...",
  "user": { "role": {} },
  "auth_state": { "code": "..." }
}
```

6. Ошибки: `422` для неверных данных/кода, `409` для существующего аккаунта с field error `phone`, `429` для лимита. Деактивированный пользователь не должен перезаписываться или автоматически активироваться.
7. Не ломай существующие `/sms/request`, `/sms/verify`, `/register`, password login и App Store review flow.

Тесты:

- успешное создание, token/user/auth_state и потребление кода;
- неверный, просроченный и повторно использованный код;
- существующий и деактивированный телефон;
- нормализация разных форматов таджикского номера;
- параллельный/повторный запрос не создаёт дубль;
- throttle и старые auth-тесты.

## 2. Безопасное удаление пользователя из админки

Добавь endpoint:

```text
DELETE /api/admin/users/{user}
```

Необязательное тело:

```json
{
  "distribute_to_agents": true,
  "agent_id": null
}
```

Требования:

1. Доступ только активным `admin` и `superadmin`: `401` без авторизации, `403` для user/agent/moderator/developer.
2. Запрети удаление собственного аккаунта (`422`).
3. Существующий `DELETE /api/user/{user}` оставь без изменения: это legacy-деактивация/увольнение.
4. Реализуй восстановимое удаление через `SoftDeletes`:
   - миграция `deleted_at` для `users`;
   - trait `SoftDeletes` в `User`;
   - перед delete: `status=inactive`, очистить `remember_token`, отозвать Sanctum tokens;
   - удалённые не попадают в обычные списки, route-model binding, поиск телефона и авторизацию.
5. Сначала обработай объявления пользователя в одной транзакции:
   - если объектов нет, параметры перераспределения не обязательны;
   - если есть — нужен `distribute_to_agents=true` или `agent_id` активного неудалённого агента;
   - нельзя выбрать удаляемого пользователя;
   - round-robin исключает inactive и soft-deleted агентов.
6. Проверь все FK пользователя. Не удаляй каскадно историю сделок, CRM, сообщений и аудита; сохрани связи либо безопасно обработай nullable согласно текущей схеме.
7. Политика повторного использования phone/email должна быть явной и протестированной. Не разрешай тихое создание дубликата удалённой личности.
8. Успешный ответ `200`:

```json
{
  "message": "Пользователь удалён",
  "id": 123
}
```

Повторное удаление — `404`.

Тесты:

- admin/superadmin могут удалить другого пользователя;
- остальные роли получают `403`;
- self-delete запрещён;
- удаление без объектов не требует перераспределения;
- пользователь с объектами требует валидного получателя;
- выбранный агент и round-robin работают корректно;
- токены отозваны и вход невозможен;
- запись скрыта из index и route binding;
- legacy-деактивация продолжает работать;
- ошибка внутри операции откатывает транзакцию полностью.
