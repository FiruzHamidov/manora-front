# Промпт для backend: безопасное удаление пользователя из админки

Репозиторий: `/Users/sarvat/Documents/GitHub/manora-backend` (Laravel).

Нужно добавить отдельный административный endpoint:

```text
DELETE /api/admin/users/{user}
```

Frontend отправляет необязательное тело:

```json
{
  "distribute_to_agents": true,
  "agent_id": null
}
```

Требования:

1. Endpoint доступен только активным пользователям с ролью `admin` или `superadmin`. Для остальных возвращать `403`, для неавторизованных — `401`.
2. Запретить удаление собственного аккаунта (`422` с понятным сообщением).
3. Не менять существующий `DELETE /api/user/{user}`: сейчас он означает увольнение/деактивацию и может оставаться для обратной совместимости.
4. Реализовать удаление безопасно через `SoftDeletes`:
   - добавить nullable `deleted_at` в `users`;
   - подключить `SoftDeletes` к `User`;
   - перед soft delete установить `status=inactive`, отозвать Sanctum tokens и очистить `remember_token`;
   - обычные списки, поиск телефона и авторизация не должны видеть удалённых пользователей;
   - уникальность телефона/email должна позволять продуктово согласованный сценарий повторной регистрации. Предпочтительно не разрешать повторное использование автоматически без отдельного restore/anonymize решения.
5. Перед удалением обработать принадлежащие пользователю объявления в одной DB-транзакции:
   - если объектов нет, разрешить удаление без `distribute_to_agents` и `agent_id`;
   - если объекты есть, требовать либо `distribute_to_agents=true`, либо валидный `agent_id` активного агента;
   - нельзя передавать объекты удаляемому пользователю;
   - round-robin не должен выбирать inactive/soft-deleted агентов.
6. Проверить остальные внешние ключи пользователя. Исторические данные сделок, сообщений, CRM и аудита не удалять каскадно; где нужно, сохранять ссылку или безопасно ставить nullable в соответствии с бизнес-правилами.
7. Успешный ответ:

```json
{
  "message": "Пользователь удалён",
  "id": 123
}
```

Статус — `200` или `204` (если `204`, без JSON; frontend допускает контракт `{message}` предпочтительно `200`).
8. Повторное удаление уже удалённого пользователя должно возвращать `404` без утечки данных.

Добавить Feature-тесты:

- admin и superadmin могут удалить другого пользователя;
- обычный user, agent, moderator и developer получают `403`;
- нельзя удалить себя;
- пользователь без объектов удаляется без параметров перераспределения;
- пользователь с объектами требует корректного способа перераспределения;
- объекты передаются выбранному активному агенту;
- round-robin исключает удаляемого, inactive и soft-deleted агентов;
- токены удалённого пользователя отозваны, повторный вход невозможен;
- удалённый пользователь исчезает из `GET /api/user` и не находится обычным route-model binding;
- старый `DELETE /api/user/{user}` продолжает выполнять деактивацию;
- транзакция откатывается целиком при ошибке перераспределения.

После реализации выполнить:

```bash
php artisan test
php artisan route:list --path=admin/users
```
